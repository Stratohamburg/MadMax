# MadMax 项目总览

更新时间：2026-10-31。`vehicle-physics-2` 已接入第一阶段驾驶验证场，包含核心车辆状态、十车型、三路面、手机摇杆、练习场、长车碰撞、四轮胎痕和验证工具；`baseline-1` 证据保留为历史，真实手机人工驾驶仍待验收。执行结果以本变更的 [验收记录](../openspec/changes/validate-driving-prototype/acceptance.md) 为准。

本文件集中说明项目大纲、核心规则、技术路线与阶段规划。已确认的产品规则、当前运行时行为和升级目标分别标注；公式和验收门槛以第一阶段 [详细设计](../openspec/changes/validate-driving-prototype/design.md) 及 [车辆物理说明](VEHICLE_PHYSICS.md) 为准。

## 1. 项目定位

| 项目 | 定义 |
| --- | --- |
| 项目名称 | MadMax，当前工作名称 |
| 游戏类型 | 以车辆驾驶为核心的冒险游戏 |
| 表现形式 | 2D 俯视角，玩家以第三人称控制小车 |
| 运行平台 | 网页版，优先适配移动端竖屏 |
| 核心输入 | 单指全向虚拟摇杆，同时表达目标速度与目标方向 |
| 操控特点 | 目标路线输入、受限前轮、接地点轮胎力、主动外拉漂移、侧滑、自动反打和转向代价；车型与路面改变响应窗口 |
| 第一阶段目标 | 验证驾驶规则、漂移可控性与手机触控体验 |
| 内容状态 | 冒险主题、具体目标、地图结构、战斗与成长尚待设计 |

项目首先需要建立稳定、可理解且能通过练习掌握的驾驶体验。玩家可以通过提前选线、小幅修正维持速度，也可以主动漂移调整姿态，并承担更大的过弯速度损失。

## 2. 体验与玩法大纲

### 2.1 驾驶体验

玩家用摇杆距离控制请求的车速，用摇杆角度选择想去的方向。车辆根据自己的加减速、转向和抓地能力逐步执行，不能瞬间改变速度或方向。

主要操作取舍包括：

- 油门深度：选择慢速精细驾驶或高速前进。
- 路线与修正：提前缓转、小幅修正更容易保速，突然急转会损失速度。
- 漂移时机：普通满油门之外继续外拉才进入漂移，在更强的姿态变化与更高的速度代价之间取舍。
- 漂移退出：主动收回到退出阈值，逐渐恢复抓地，为后续路线调整做准备。

### 2.2 第一阶段体验闭环

```text
Enter Playground --> Drive --> Observe --> Reset / Tune
                        ^                       |
                        +-----------------------+
```

第一阶段提供可重复驾驶的验证场，帮助判断操作是否容易理解、是否误触漂移、细微转向能否保速，以及实际侧滑是否可控。

### 2.3 后续冒险内容

后续需要围绕驾驶能力设计探索、目标与环境挑战。以下是需要补齐的设计章节，尚不代表已经确定的功能清单：

| 章节 | 需要确定的内容 |
| --- | --- |
| 世界与主题 | 游戏发生的环境、氛围、视觉风格及叙事表达 |
| 主要目标 | 玩家每次游玩需要完成什么，驾驶如何帮助完成目标 |
| 地图组织 | 开放探索、区域推进或关卡结构；路线与事件如何分布 |
| 环境交互 | 路面、障碍、交互物与驾驶能力之间的关系 |
| 挑战与失败 | 什么构成威胁，何时失败，如何重试与恢复 |
| 战斗 | 是否包含战斗，以及它与单摇杆驾驶的输入关系 |
| 车辆与成长 | 车辆如何获得、如何区分手感、是否存在改装与成长 |
| 进度与保存 | 哪些状态需要跨会话保存，何时保存 |

这些内容应先形成独立提案，再进入对应阶段实施。

## 3. 界面与输入布局

已确认采用竖屏上下布局：上方游戏主视图至少占当前可见视口高度的 60%，下方为摇杆操控区。HUD 和重置入口可以放在主视图中。

```text
+--------------------------------+
| HUD / RESET                    |
|                                |
|          GAME VIEW             |
|            >= 60%              |
|                                |
+--------------------------------+
|                                |
|         VIRTUAL STICK          |
|          + DRIFT RING          |
|                                |
+--------------------------------+
```

操控区需要容纳完整的全向漂移行程，并扣除设备安全区。第一阶段默认采用固定中心摇杆和不随车头旋转的跟随镜头，使摇杆方向始终对应稳定的屏幕方向。

目标检查尺寸为 320×568、360×640、390×844 CSS 像素。浏览器工具栏变化时按新的可见视口重新布局，并清除旧触控，避免中心位置变化后残留错误输入。

## 4. 已确认的驾驶规则

摇杆方向与距离表达世界路线和速度期望。任意非零位移有正目标速度，精确回中或结束输入请求停车；输入最大目标封顶不截断物理实际速度。前后驱动、制动和前轮命令由有限控制器输出。

普通控制根据车型、速度、载荷和路面限制前轮与牵引请求，在稳定驾驶矩阵中避免自身诱发spin。已有失控、碰撞或抓地突变仍可能使车辆倒滑、旋转或继续失控，控制器只尝试恢复。

普通最大目标半径R之外有缓冲行程，继续外拉至Renter进入漂移，回收到Rexit退出，满足R<Rexit<Renter。漂移只放宽控制策略并请求后轴制动等执行器，不改变物理轮胎材质。漂移中的动力继续改变轨迹，实际滑移消耗动能；退出不清实际侧滑或横摆。

物理不感知普通/漂移模式，只接收执行器、物理参数和路面。实际beta、u、speed、r不按期望限制。静止打轮不自行产生横摆，零质心速度但已有旋转会继续受接地点摩擦作用。胎痕依据接地点滑移和功率，支持纯旋转及动力空转。

碰撞由车身接触点冲量改变平移和横摆，不统一停车、不注入逃离速度。重置是独立操作，清车辆、控制历史、输入、镜头、时钟与胎痕。

## 6. 技术路线

以下为当前客户端和升级目标共同采用的技术路线。实际依赖由根目录 `package-lock.json` 锁定，运行版本记录在验收记录中。

| 层次 | 方案 | 选择依据 |
| --- | --- | --- |
| 开发语言 | TypeScript | 为车辆状态、参数和输入建立明确类型，支持独立测试 |
| 开发与构建 | Vite、npm | 提供本地开发、手机局域网访问与静态构建入口 |
| 场景渲染 | Canvas 2D | 满足单车、静态场地和拖尾绘制，便于控制物理与绘制边界 |
| 界面 | HTML、CSS、DOM 控件 | 承载摇杆、HUD、安全区布局和验证面板 |
| 输入 | Pointer Events | 统一触摸与鼠标，支持活跃触点捕获及取消清理 |
| 车辆模拟 | `vehicle-physics-2` TypeScript 低速运动学/中高速单轨动力学、轮胎力和 RK2 子步 | 核心与网页固定时钟回放已实现 |
| 时间推进 | 1/120 秒固定物理步长，requestAnimationFrame 渲染与插值 | 减少不同渲染频率造成的操控差异 |
| 碰撞 | 按核心车身保守占地对静态矩形与边界扫掠，碰撞停车清动态历史，切向空间可脱离 | vehicle-physics-2 接入已实现 |
| 行为测试 | Vitest | 验证速度、角度、模式切换及跨时间输入结果 |
| 浏览器测试 | Playwright | 验证竖屏布局、触控生命周期与整体交互 |
| 需求与规划 | OpenSpec 1.15.0、spec-driven | 用提案、规范、设计和任务管理行为变更 |
| 构建交付 | 静态网页产物 | 第一阶段无需后端；部署位置按后续发布需求决定 |

开发环境要求为 Node.js `^20.19.0 || >=22.12.0`，与 Vite 引擎要求一致；本轮实际使用 25.9.0。安装、启动与验证命令见 README。

Canvas 2D 适合当前场景规模小、物理规则明确的验证场。车辆升级采用单轨/自行车模型而非通用物理引擎，是为了让轴距、轮胎力、横摆、辅助和游戏代价可以分别观测；这仍是可调的游戏近似，不是真实车型标定。未来若地图组织、动画与资源管理复杂度增加，再评估引入 Phaser 等框架；车辆行为合同和独立测试应继续保留。

### 6.1 vehicle-physics-2 模块与兼容

车辆模块按几何、轮胎、转向控制器和动力积分职责拆分。权威状态使用世界速度向量、车头、横摆角速度、实际前轮转角、漂移混合量和控制历史；`speed` 与 `motion` 只读派生。碰撞、四轮绘制、胎痕和验证面板读取同一套轴几何。

旧 `baseline-1` 的 `normalTurn`、`driftTurn`、`normalGrip`、`driftGrip` 不能直接解释为新版前轮角或轮胎刚度；被取代的 `axle-dynamics-1` 也明确拒绝。当前 profile 通过 `validateProfile/applyProfile` 原子应用，迁移规则和当前局限见 [车辆物理说明](VEHICLE_PHYSICS.md) 与 [参数说明](PARAMETERS.md)。

## 7. 架构与数据流

### 7.1 模块边界

```text
Touch / Mouse --> Input Intent --> Fixed Physics --> Vehicle State
                      |                 |                  |
                      v                 v                  v
                Input Feedback    Static Collision     Canvas View
                                                            |
                                                            v
                                                      HUD / Debug
```

- 输入层只负责输出目标速度、目标方向、方向是否有效和漂移状态，不直接移动或旋转车辆。
- 模拟层读取输入与车辆 profile，输出权威位置、世界速度、车头、前轮、横摆、漂移混合及可观测的动力贡献。
- 场景层提供边界与障碍，碰撞处理与车辆位移共同完成每个模拟步。
- 绘制层读取状态及镜头，不使用绘制帧数改变物理结果。
- 验证层观察同一份状态，参数修改经过合法性检查后通过重置应用。

### 7.2 时间与坐标

车辆物理使用世界单位、秒和弧度；输入使用 CSS 像素，绘制根据镜头和设备像素比转换。需要分别处理 CSS 尺寸与画布实际像素，防止高分屏导致触点位置与显示位置错位。

输入按时间标记供固定步长采样。页面隐藏时清除输入、暂停模拟并丢弃积压；恢复后重建时钟，不补算后台位移。前台异常长帧采用积压上限。

### 7.3 参数与资源

车辆使用一组集中参数描述最高速度、加减速曲线、普通与漂移转向曲线、抓地、侧滑上限和转向减速。新增车型优先增加参数配置，沿用同一套行为规则。

场地、车辆与拖尾先使用简洁几何表现，资源随客户端静态加载。正式美术、声音与内容资源管理在后续内容需求明确后扩展。第一阶段不建立账号、联网或进度存档服务。

## 8. 阶段规划

第一阶段已经形成具体提案；后续阶段为建议推进顺序，需要各自确认范围与建立变更。

| 阶段 | 目标 | 主要产出 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 第一阶段：驾驶验证 | 证明单摇杆驾驶、转向与真实漂移可控 | 一辆测试车、验证场、拖尾、调参观测、测试与验收记录 | 行为与浏览器检查通过，完成真实手机驾驶评估并处理主要问题 |
| 第二阶段：冒险体验样例 | 确定驾驶服务于什么游戏目标 | 围绕已确认目标的一小段地图、交互与完整游玩流程 | 玩家能够理解目标，驾驶与目标之间形成可重复体验 |
| 第三阶段：内容与车辆差异 | 扩展已验证的冒险体验 | 按后续提案增加区域、事件与不同手感车辆，成长是否加入另行决定 | 新内容能复用已有规则，车型差异可理解且可验证 |
| 第四阶段：体验与交付完善 | 达到选定设备和浏览器上的发布要求 | 正式表现、性能与兼容性优化；按实际需求加入保存及发布配置 | 完成对应提案约定的质量与发布验收 |

阶段顺序不对应已承诺的工期。第一阶段验证结论可能要求继续调整驾驶模型，再决定后续内容范围。

## 9. 第一阶段范围与验收

### 9.1 交付范围

一辆参数可调测试车、包含直道与不同曲率弯道的场地、少量静态障碍、完整虚拟摇杆、普通与漂移驾驶、侧滑拖尾、固定方向跟随镜头、HUD、重置和单独开启的验证模式。

碰撞提供防穿透、有效接触冲量、摩擦与横摆响应，不包含伤害流程；无法驶离的封闭死角可通过重置恢复。

### 9.2 验收分层

| 层次 | 主要内容 |
| --- | --- |
| 行为性质 | 非零输入有目标速度，实际状态由有限执行器与物理产生，低速接触耗散 |
| 操控规则 | 漂移外拉缓冲与滞回、控制器包络随车型/速度/载荷/路面变化，真实侧滑与连续恢复 |
| 能量收支 | 组合滑移、制动、阻力和碰撞损失来自实际运动，无意图夹角扣速 |
| 时间一致性 | 相同输入以 30/60/120 FPS 驱动渲染时物理结果一致，后台恢复无位置跳跃 |
| 浏览器交互 | 三种目标尺寸、完整漂移行程、安全区、越界捕获、多指与中断清理 |
| 场景反馈 | 防穿透、接触脱离、拖尾有界、漂移中重置能清除完整状态 |
| 实机手感 | 至少一台真实手机驾驶，记录误触、连续漂移、精细保速与连续弯表现 |

跨帧率测试用于验证物理结果一致性，流畅度另记录真实设备上的运行表现。浏览器仿真和手机实测分别记录，没有实机证据时整体验收保持未完成。

详细容差、起始参数和验证矩阵见 [设计文档](../openspec/changes/validate-driving-prototype/design.md)；逐项实施与完成证据见 [任务清单](../openspec/changes/validate-driving-prototype/tasks.md)。

当前三份能力规范属于进行中的变更，尚未归档成为 `openspec/specs/` 中的生效规范。网页消费者迁移和桌面回归已完成，真实手机人工驾驶尚未完成，因此第一阶段整体验收保持未完成。

核心物理的独立入口是 `src/vehicle/physics/index.ts`，运行 `npm run physics:benchmark` 和 `npm run physics:audit` 可复核 `vehicle-physics-2`、`vehicle-profile-2`、`vehicle-surface-1`、十车型以及干硬路、松散地、湿滑地证据。`build-vehicle-physics` 只负责无 DOM 物理核心和基准；`validate-driving-prototype` 负责输入、网页场景、碰撞、绘制、触控和手机接入。核心报告通过不能替代消费者迁移或真实手机验收。

## 参考资料

模型升级使用以下资料解释关系，不复制完整论文或库实现，也不声称真实车辆标定：

- [Bicycle Model and Ackermann Geometry](https://thomasfermi.github.io/Algorithms-for-Automated-Driving/Control/BicycleModel.html)：轴距、瞬时转动中心、前后轴路径和参考点。
- [CommonRoad Vehicle Models 3.0.2](https://pypi.org/project/commonroad-vehicle-models/3.0.2/)：运动学、单轨动力学、漂移和低速模型。
- [Stanford 漂移控制研究](https://ddl.stanford.edu/publications/journal/towards-automated-vehicle-control-beyond-stability-limits-drifting-along)：速度方向、车身横摆与侧滑的联合观察。
- [Project Chrono Wheeled Tire](https://api.projectchrono.org/wheeled_tire.html)：非线性轮胎、组合滑移与复杂度取舍。
