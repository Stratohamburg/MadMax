# MadMax 游戏愿景

> **状态：产品愿景与设计护栏。对应八项玩法已在本地实现并接入，真实手机驾驶和性能尚待验收；变更尚未归档。**
>
> 本文从正在评审的 OpenSpec Proposal 中提炼共同目标，用于约束后续产品与技术决策。具体范围、验收标准和实施顺序仍以各 Proposal、Design、Tasks 及归档后的正式 Spec 为准。

更新时间：2026-11-01。

## 1. 一句话定位

MadMax 面向移动端竖屏，是一款以单指驾驶为核心的 2D 俯视角废土车辆游戏：玩家通过空间化车辆装配形成独特 build，在自动战斗和局内肉鸽成长中突围，并以高风险的搜打撤循环积累局外资源。

核心体验可概括为：

```text
可练习的物理驾驶 × 具象的车辆构筑 × 自动化战斗 × 高风险撤离成长
```

## 2. 产品支柱

### 2.1 所拼即所得

改装不是抽象装备栏。部件的形状、占用位置、质量和外露方向都应具有可感知后果：

- 内层容纳发动机、变速箱、电池、油箱、座舱和内装甲；外层容纳武器、车顶组件与外挂装甲。
- 装配清单派生总质量、质心、转动惯量、轴荷、抓地与动力链参数，影响加速、转向、漂移和碰撞表现。
- 受损部件先进入性能衰减的 `Damaged` 状态，归零后进入失去功能的 `Destroyed` 状态；损坏应同时影响 build 和驾驶决策。

玩家应能从车上“看懂”装配，并从实际操控与战斗结果中感受到每个取舍。

### 2.2 单手驾驶，自动战斗

单摇杆始终优先服务于速度、路线、车头和主动漂移；战斗深度来自车辆朝向、挂点位置、射界、走位与 build，而不是额外堆叠瞄准或开火输入。

- 炮台、固定朝向、制导和被动事件武器均自动触发。
- 固定步长的纯逻辑战斗负责目标选择、弹丸、伤害和后坐力，绘制不改变结算。
- 战斗信息必须服从“驾驶第一”：车身周围 1.5 倍半径保持视觉净空；射界投影在地面，装填与过热使用射界外沿光弧；模块损伤集中到不遮挡驾驶视线的状态 HUD。

### 2.3 从脆弱突围到弹幕成型

一局开始时，有限装配、弹药、供电和耐久要求谨慎驾驶。局内的三选一修饰符、标签联动与相邻协同逐步放大已选择的 build，使玩家获得从小规模交火到高密度弹幕和高额伤害的明确成长曲线。

数值增长必须是可诊断、可控的：修饰符区分 flat、加算与乘算层；标签和叠加上限可追踪；高负载战斗须在目标移动设备性能预算内验证。

### 2.4 贪婪与撤离

单局核心不是清空所有敌人，而是在风险、收益和撤离时机之间决策：

```text
选择装配 → 进入区域 → 驾驶、战斗、搜刮与获得局内加成
    → 判断是否继续深入 → 撤离成功 / 失败 → 结算并改变局外仓库
```

战利品占用有限空间；成功撤离才能稳定带出，失败会依据明确规则损失战利品和/或装配部件。机械师与移动维修区提供局内修复选择，但不应消除失败风险。

## 3. 双层成长循环

### 局外：车库与长期成长

玩家在试车场改造的营地驾驶，开到出生点前方的商店、装备或出击区域并停稳进入。局外保存部件仓库、货币/材料、解锁、装配方案、主线进度与统计。车库中的双层网格工作台以外观和底盘俯视呈现车辆，正方格上的多格部件显示完整外形，让玩家加载出厂预设或自由组装，并在出击前预览质量、质心、动力、极速、供电与弹药。

本地档案必须版本化、可校验、可迁移，并在副本结算时原子写入，避免异常退出造成战利品复制或丢失。

### 局内：副本与临时构筑

副本以区域、敌人波次、搜刮点、撤离点、Boss 和叙事节点组织。局内修饰符只对当前 run 生效；成功或失败后按结算规则回写局外档案。

局内构筑与局外装配的职责应保持清晰：

| 层次 | 主要决定 | 是否跨局保留 |
| --- | --- | --- |
| 局外装配 | 底盘、部件布局、基础质量、动力与初始武器 | 是 |
| 局内修饰符 | 标签强化、倍率、临时协同与战术方向 | 否 |
| 副本结算 | 战利品、损耗、货币、解锁与统计 | 结算后写入 |

## 4. 设计护栏

后续提案应通过以下检查，若偏离则需明确更新本愿景：

1. **驾驶输入不可被稀释**：常规战斗不增加瞄准摇杆、开火键或复杂多指操作。
2. **构筑必须空间化**：优先使用双层网格、部件形状、朝向、质量与邻接关系，避免退化为纯文本装备槽。
3. **模拟必须可复现**：物理、战斗、随机性与结算在固定步长、可播种的逻辑层中运行；DOM 和渲染仅消费结果。
4. **信息不得遮挡车辆**：任何射界、装填、伤害和损毁提示都不得破坏车身姿态、前轮和漂移的可读性。
5. **风险必须可理解**：撤离条件、容量限制、损耗、维修边界和结算结果应在玩家做出承诺前可预期。
6. **性能是玩法约束**：大量弹丸、敌人和特效必须采用池化、聚合和上限策略，并以目标移动设备基准验证。

## 5. 愿景能力地图

| 能力 | 愿景职责 | 依赖 |
| --- | --- | --- |
| `loadout-grid` | 双层底盘、部件形状、摆放约束与稳定装配清单 | 驾驶底盘数据 |
| `assembly-physics` | 装配到质量、质心、轴荷、动力链和喷射的派生 | `loadout-grid`、车辆物理 |
| `auto-weapons` | 自动索敌、射界、冷却/过热、后坐力与目标选择 | `loadout-grid`、`assembly-physics` |
| `combat-damage` | 敌人、弹丸、伤害、两段损毁、维修与性能预算 | `auto-weapons`、场景碰撞 |
| `roguelike-modifiers` | 标签、协同、修饰符层级、候选生成与数值诊断 | 装配、物理、武器、战斗 |
| `pve-extraction-mode` | run 生命周期、区域、搜刮、撤离、失败与结算 | 上述局内能力 |
| `progression-persistence` | 档案、存档迁移、局外成长与结算入档 | 装配、PVE 结算 |
| `vehicle-ui` | 改装工作台、状态纸娃娃与射界可视化 | 装配、武器、战斗 |
| `driving-hub` | 可驾驶营地主界面、停车进入商店/装备/出击及返回营地 | 驾驶、装配、档案、工作台与副本 |

推荐的基础实施链路为：

```text
loadout-grid → assembly-physics → auto-weapons → combat-damage
                                      ↓
                         roguelike-modifiers → pve-extraction-mode
                                                      ↓
                                      progression-persistence / vehicle-ui
```

`vehicle-ui` 可以在其消费的数据契约稳定后并行推进；它不应自行定义或复制核心规则。

## 6. 当前边界

- 当前已实现驾驶验证场、双层装配、装配物理 v4、自动战斗、模块损毁、肉鸽升级、废弃货场搜打撤、原子本地档案和工作台。默认首页 `/` 为驾驶营地；副本入口为 `/?mode=pve`，练习场为 `/?mode=practice`；使用说明见 [营地](DRIVING_HUB.md)、[副本](PVE.md)、[档案](PERSISTENCE.md) 和 [车库](VEHICLE_UI.md)。
- 桌面逻辑、浏览器和布局验证独立于真实手机；当前未完成手机驾驶手感及战斗压测，不能视为移动端整体验收通过。
- 本愿景不承诺 PVP、账号系统、云存档或联网匹配；未来可在不破坏确定性核心的前提下另行提案。
- Canvas 2D 仍是当前渲染路线。是否更换框架取决于实际内容规模与性能验证，不能仅因愿景而提前引入。
- 世界观文案、剧情内容、具体数值、正式美术与音频不在本文定义范围内。
