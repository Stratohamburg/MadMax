# Design

## Context

当前项目无任何持久化。存档格式一旦发布就必须长期兼容，需要先固定版本与迁移机制。

## Decisions

- **介质**：首版用 IndexedDB（容量大、可事务），封装为抽象存储接口，便于测试用内存实现与后续换云存档。
- **事务与幂等**：结算携带唯一 runId，档案记录已入档 runId 以防重复；单事务写入。
- **完整性**：序列化后附哈希；保留最近一份备份。
- **迁移**：版本链式迁移函数，每个版本有 fixtures 测试。
- **引用而非复制**：方案与仓库只存部件实例 ID 和定义 ID，定义来自数据表，与 loadout 的序列化原则一致。
- **PVP 预留**：档案结构不含对战数据，后续以新字段加迁移方式扩展。

## Risks / Trade-offs

- 本地存档可被篡改，本期不防作弊；PVP 阶段再评估服务端校验。
- 浏览器清理站点数据会丢档；后续可提供导出/导入。

## Implementation Decisions

- 存档 schema 2，规范化 JSON 加 FNV-1a 校验（检测意外损坏，不作防作弊）；IndexedDB 单记录同时存主档、上一有效备份与待入档结算。内存实现与浏览器实现共享同步事务回调。
- schema 1 的显式迁移补齐实例等级/耐久与已入档 runId；未来版本即使有旧备份也拒绝加载，完全保留原数据。主档损坏时仅回退有效备份，并展示恢复提示；两份均坏阻止覆盖。
- 终局先持久化 pending，再在一个 readwrite 事务内应用奖励/损失/统计、记录 runId、更新备份并清除 pending。启动重放未完成 pending；多标签页事务串行，避免复制奖励。
- 新档给跑车、初始实例、250 货币与 100 废料。出厂预设只匹配已拥有实例，不生成免费部件；缺失项明确列出。购买零件 50 货币/10 废料；解锁底盘或部件 100/20；升级每级 50×新等级/10×新等级，上限 5。
- 等级每级增加对应武器伤害或发动机动力 5%，耐久按现有模块 hp 保存；已毁坏内部件在车库花 20 货币/5 废料维修。入局按实例耐久初始化，不重置伤害。
- 装配保存、命名、删除、加载均校验库存引用；蓝图保留缺失实例便于显示，不复制物品。本期不新增导入/导出流程。
